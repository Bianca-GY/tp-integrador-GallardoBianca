# Diagrama de flujo — RET-002

## Límite de butacas ocupantes por usuario y evento

```mermaid
flowchart TD
    A["HTTP POST /events/{event_id}/holds"] --> B["API<br/>app/api/routes.py"]
    B --> C["Caso de uso<br/>app/application/use_cases.py"]

    C --> D["Verificar evento"]
    D --> E["Verificar butaca"]
    E --> F["Consultar retenciones<br/>de la butaca"]

    F --> G["Validar RET-001"]
    G --> H["Consultar retenciones ocupantes<br/>del usuario + evento"]

    H --> I["Validar RET-002"]

    I --> J{"¿Tiene menos<br/>de 4 ocupantes?"}

    J -->|No| K["409 Conflict<br/>RET-002"]
    J -->|Sí| L["Crear retención"]
    L --> M["201 Created"]

    N["ACTIVE / CONFIRMED"] --> H
    O["EXPIRED / RELEASED"] --> P["No cuentan"]
    P --> H
```

## Estados considerados

- `ACTIVE`: cuenta como butaca ocupante.
- `CONFIRMED`: cuenta como butaca ocupante.
- `EXPIRED`: no cuenta.
- `RELEASED`: no cuenta.

## Alcance de la garantía

La implementación actual realiza la secuencia:

**leer → validar → insertar**

La verificación secuencial está cubierta por los tests y la colección de Postman. La operación todavía no es atómica frente a solicitudes concurrentes, por lo que no se afirma una garantía completa bajo concurrencia.
